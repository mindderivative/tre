# Log: Phase 2, Step 1 -- Zero-Allocation Ring Buffers & Transient Pools

## Doc gaps found

### TECHNICAL.md Section 3.4 described the zero-allocation guard in leftover C++ terms
"`operator new`/`operator delete` (and `malloc`/`free`)" and "`NDEBUG`" are C++ concepts with no Rust equivalent to override in the same way. Fixed to describe the real Rust mechanism: a custom `#[global_allocator]` wrapper implementing `GlobalAlloc`, gated by `cfg(not(debug_assertions))`. Found while reading this section during planning, before any code was written.

## Real bugs found (both caught by actually running the code under the Vulkan validation layer, not by code review)

### An initial fence-rotation design broke every existing single-command-buffer example
Building the ring buffer's segment-tracking, the first version gave `VulkanDevice` 3 separate fences (one per frame-in-flight slot) and made `begin_frame`/`submit_and_present` wait on/signal whichever one the current rotation index pointed to. This looked correct in isolation but is unsound: `VulkanDevice` reuses ONE persistent command buffer every frame regardless of which ring-buffer segment is logically current. Waiting on a *different* fence than the one that exact command buffer's own last submission signaled proves nothing -- a freshly-rotated-to fence is trivially already signaled (it was created signaled and has no history yet), so the wait passes immediately even if the GPU is still mid-flight on that same command buffer from the previous frame.

**How it was caught:** re-running `walking_skeleton` and `multi_window` under `VK_LAYER_KHRONOS_validation` (the same discipline this project has followed since Phase 0) immediately threw `VUID-vkResetCommandBuffer-commandBuffer-00045` ("in use"), `VUID-vkBeginCommandBuffer-commandBuffer-00049` ("before it has completed"), `VUID-vkQueueSubmit-pCommandBuffers-00071` ("already in use"), and `VUID-vkAcquireNextImageKHR-semaphore-01779` ("pending operations"). Both examples still visually completed (the GPU is fast enough locally to usually finish before the next frame regardless of whether the CPU actually waited for it), which is exactly why running under validation layers -- not just watching the output look plausible -- caught a real, latent race that would be very difficult to reproduce and debug on different hardware or under load.

**Resolution:** reverted to a single real fence for command-buffer gating, byte-for-byte the same semantics Phase 0 built (`in_flight_fence`, renamed `frame_sync.fence`). Added a SEPARATE, purely informational `AtomicUsize` counter for the ring buffer's own segment selection, advanced once per frame after the real fence signals. This is sound without its own per-segment fence precisely because the one real fence already fully synchronizes every single frame -- by the time the counter cycles back to a given value, at least two other fully-synchronous frames have completed since that segment was last written to. Re-verified all five Vulkan examples (`walking_skeleton`, `multi_window`, `headless`, `input_demo`, the new `memory_pools_demo`) with zero validation errors after the fix.

### Pooled transient textures were never destroyed at device teardown
`VulkanDevice` had no logic to walk its transient pool and destroy checked-in (available, not currently acquired) textures before destroying the device itself.

**How it was caught:** the new `memory_pools_demo`'s very first run under validation layers reported `VUID-vkDestroyDevice-device-05137`: 6 leaked objects at `vkDestroyDevice` (2 `VkDeviceMemory`, 2 `VkImage`, 2 `VkImageView` -- exactly the two textures the demo had acquired-then-released back into the pool and never re-acquired before exit).

**Resolution, and why the obvious fix would have been worse:** simply adding the pool as an ordinary struct field and relying on Rust's automatic field-drop would NOT have fixed this correctly -- Rust drops a struct's other fields only *after* an explicit `Drop::drop` body returns, so the pool's own automatic drop would run each pooled texture's destructor (which calls `destroy_image_view`/`destroy_image`/`free_memory` against the device) AFTER `Drop for VulkanDevice`'s existing body had already called `destroy_device`. That would trade one confirmed bug (a leak) for a worse, silent one (use-after-free against an already-destroyed `VkDevice`). Fixed by explicitly clearing the pool (running every pooled texture's real destructor) at the START of `Drop for VulkanDevice`'s body, before the existing fence/command-pool/device/instance teardown sequence.

## Scope deviations from IMPLEMENTATION.md Step 2.2's literal task wording (deliberate, not omissions)

* Task 3's 64-byte CPU-thread-boundary padding (false-sharing protection) was not implemented -- there is no multi-threaded canvas writer yet that could actually race on this buffer (Phase 5's `SubCanvas` is what would introduce one). Padding against a hazard nothing yet exercises can't be verified as correct or even necessary; deferred until Phase 5.
* Task 4's "hook this into `Canvas::push_layer` for immediate zero-allocation acquisition" was not done as literally worded. `RenderingCanvas::push_layer`/`pop_layer` record IR markers and the debug balance counter only -- they never call `RhiDevice::acquire_transient_target`. Wiring `Canvas` directly to a concrete RHI device would violate DESIGN.md Section 2.2's "Strict Architectural Separation of Concerns" (Canvas recording is pure, backend-agnostic IR construction, matching how `draw_rounded_rect` already works with no RHI reference at all), and there is no consumer downstream of `Canvas` yet that would actually use an acquired transient target (Phase 6's sort/batch/execute pipeline is what would). The transient pool itself is real, independently implemented, and independently proven via `demo/phase2_step1/`; wiring `push_layer` to it is deferred to whichever phase builds that consuming pipeline stage.

## Verification performed

- `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo build --workspace --all-targets`, `cargo test --workspace`: all clean, including 3 new `tre-engine` unit tests for `push_layer`/`pop_layer`'s balance assertion (balanced calls don't panic, an unbalanced `push_layer` panics at `flatten()`, a bare `pop_layer` panics immediately).
- New `crates/tre-rhi-vulkan/examples/memory_pools_demo.rs`, run against real hardware (AMD Radeon 890M) with `VK_LAYER_KHRONOS_validation` enabled: zero errors (after fixing the two bugs above). Proves, with real assertions on the printed output, not just "it ran without crashing":
  - The ring buffer's segment rotation is genuinely 0, 1, 2, 0, 1, 2, ... across 7 real frames driven through a `HeadlessSwapchain`, with every returned write offset 256-byte aligned.
  - The transient pool reports exactly 1 miss then 19 consecutive hits across 20 acquire/release cycles at the same size, and exactly 1 additional (isolated) miss for a different, never-before-requested size -- steady-state reuse, not per-cycle allocation.
- All three Step 1 Vulkan examples (`walking_skeleton`, `multi_window`, `headless`) plus `input_demo` re-run under validation layers after the `FrameSync` fix, to confirm no regression: zero errors across all four.
