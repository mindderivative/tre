# Release checklist

The release process is written in `docs/contributing.md` ("Branches and releases") and `.github/workflows/`. This skill is the ordered checklist, with the stops that need the user.

**Standing rule (CLAUDE.md): commit locally only. Pushing, opening a pull request, merging, tagging and approving the PyPI environment each need the user's separate, explicit instruction. A past approval does not carry over to the next release.**

## 1. Pre-flight (read-only)

- On the release branch (`0.5.x`, cut from `main`), with a clean `git status`. If the branch or version the user names is not there, or the version in `Cargo.toml` is still the previous release, say so and ask which branch holds the work before planning anything else.
- Every issue in the release is in **In review** or **Done** on the GitHub project, each with a comment of what was checked and what was not.
- Open issues that are held for hardware (#187 for Windows and #188 for macOS at last count) are listed in the release notes as not verified, not silently dropped.
- Check the version is free: PyPI never accepts the same version twice (`pip index versions tesserae-engine`, or the project page).

## 2. Version

The version appears in `Cargo.toml` (`[workspace.package]`), `pyproject.toml` and `Cargo.lock`. Bump all three on the branch. Then search for the old version string to see where else it is written. Guide pages carry historical "0.5.7:" notes saying when a feature arrived; leave those alone, they are not the current version.

If the minimum Rust version changed, `rust-version` in the root `Cargo.toml` and `msrv` in `ci.yml` move together (the file explains how the floor is derived).

## 3. Checks

```bash
tools/verify.sh --cross
```

It stops at the first failure. It covers rustfmt, clippy with warnings as errors, Rust tests (also with `TRE_DAMAGE_VERIFY=1`), `maturin develop`, the generated `docs/api/python.md`, stubtest, `mypy --strict`, pytest (also damage-verified), `mkdocs build --strict`, and with `--cross` the Windows and macOS clippy runs and the MSRV build.

Afterwards:
- `git status` for `docs/api/python.md` (regenerated by the script) and, if a public Rust item changed, regenerate `docs/api/rust.md` (commands in `docs/contributing.md`). Commit what changed.
- Live-window tests skip without a display. If there is none, say that they did not run.
- If the renderer pin moved, run the `pixel-test-triage` checks and a `perf-profiling` before/after.

## 4. Documentation

- `LOG.md`: the Status section and a dated entry for what shipped, in the existing style.
- A `docs/migrating-<version>.md` page if anything a user writes changed, and the `mkdocs.yml` nav entry for it.
- `README.md` and `docs/installation.md` if install steps or requirements changed.
- Built with `mkdocs build --strict` (done by `verify.sh`).

## 5. Commit, then stop

Commit on the branch in the repo's style (`<version>: what it does (#issue)`; check `git log`). Then tell the user what is ready and wait.

## 6. Steps that need the user's instruction, in order

1. Push the branch and open the pull request into `main`; `ci.yml` runs on it. Because the workspace version moved, `tools/ci_plan.py` picks the **full tier** (Linux, Windows, macOS, MSRV, every example, the docs build); check the plan in the run summary says `full`. The result to read is `CI result`. Read the result, including the Windows and macOS jobs, which are non-blocking for tests and may be red or green for reasons worth reporting.
2. Merge. The merge deploys the docs (`docs.yml`).
3. Tag the merge commit `vX.Y.Z`, annotated, and push the tag. This starts `wheels.yml`, which builds the wheels and sdist and creates the GitHub Release.
4. A reviewer approves the **`pypi` environment**. Only then does the upload happen (trusted publishing). Claude does not approve this.
5. Verify: `pip install tesserae-engine==X.Y.Z` in a clean venv, `import tre`, and run one example headless.

Move the issues to **Done** and update the memory entity (`tre-v2-gui-framework`) only after step 5 succeeds.

## Report

Say what was run and what passed, what was skipped and why, and which issues remain held. Do not write "released" until step 5 has been seen to work.
