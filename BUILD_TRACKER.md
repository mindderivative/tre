## Milestone 50 — Theme-Driven Shape & Elevation for the Imperative MD3 Catalog (§5, §7, §7.1)

**Status: ✅ Complete — all 5 phases.** User-directed: "Scope the corner-radius/elevation to use the new theme pattern. ## Milestone 87 — Thread-Safe Callbacks into a Running `App` (issue #6)

**Status: ✅ Complete (2026-09-25).** [`tre` issue #6](https://github.com/mindderivative/tre/issues/6), filed by the Tesserae session after its M29 moved all file handling out of `tre`: nothing can hot-reload a live window. `App.run()` (`engine-py/src/app.rs:384`) hands control to `run_windowed_multi` until every window closes, and from then on Python only runs inside input handlers and accessibility actions. `View`/`Window`/`App` are all `#[pyclass(unsendable)]`, so a background thread can't touch them, and an idle loop sleeps in `ControlFlow::Wait`. This isn't new: `tre`'s own `poll_reload()` has never worked inside `App.run()` either (`examples/hot_reload.py` only runs it headless).

The issue proposed `app.set_interval(0.25, watcher.poll)`. User's direction (2026-09-25): "I would prefer the threadsafe option more and tesserae will end up moving to a watcher driven by file-change events." So M87 builds a thread-safe callback queue instead of a timer: a background thread (e.g. a `watchfiles` watcher) queues a callable, the idle loop wakes, and the callable runs on the event-loop thread where it can call `view.reconcile(spec=...)`. No polling, no wasted wake-ups.

**Design decisions (made while scoping, from direct source reads):**
- **Reuse `Terminal`'s own cross-thread pattern exactly.** `TerminalSession`'s PTY reader thread (`engine-py/src/terminal.rs`) already pushes into a shared queue and calls `EventLoopWaker::wake()` (`engine-platform/src/lib.rs:286`, M31 Phase 6); the waker is installed from `run_windowed_multi`'s `setup` closure (`app.rs:1224`) and the main thread drains in its per-frame hook. The callback queue is the same shape with `Py<PyAny>` callables in it -- no new `engine-platform` event type needed, since `PlatformEvent::Wake` already requests a redraw of every open window.
- **A separate `Send + Sync` handle object, not a method on `App`.** `App` is `unsendable`: pyo3 rejects any method call on it from a thread other than the one that created it. So `App.thread_handle()` returns a `#[pyclass(frozen)]` `LoopHandle` (holding only `Arc`s -- the queue and the waker slot) that a background thread can hold and call `handle.call_soon(fn)` on. This mirrors asyncio's `call_soon_threadsafe` semantics while respecting pyo3's thread rules.
- **No `set_interval` in this milestone.** The user preferred the thread-safe option; a timer can be layered on later (a background thread calling `call_soon` on a schedule already gives one, in pure Python).

### Phase 1 — Callback Queue, `LoopHandle`, Drain ✅
- Step 1: shared state in `engine-py` -- a queue of `Py<PyAny>` callables plus an `Option<EventLoopWaker>` slot, both behind `Arc<Mutex<...>>`, owned by `App`; `run_windowed_multi`'s `setup` closure installs the waker the same way it already does for terminal sessions — ✅ (`CallQueue` in new `engine-py/src/thread_handle.rs`; the waker is cleared again when `run()` returns)
- Step 2: `App.thread_handle() -> LoopHandle`, a frozen `Send + Sync` pyclass; `LoopHandle.call_soon(fn)` rejects a non-callable with `TypeError`, pushes, and wakes the loop; safe from any thread, before, during, or after `run()` — ✅ (the compiler enforces `Send + Sync`: a non-`unsendable` pyclass that isn't both fails to build)
- Step 3: drain on the event-loop thread at the top of the per-frame hook, before the dirty gate -- FIFO, each callable run with the GIL held, an exception reported via `dispatch::log_uncaught_exception` without stopping the loop or the rest of the queue; after draining at least one callable, wake again so every window re-checks its dirty flag, since a callback run during window A's frame may have changed window B's tree — ✅ (the queue is taken whole and the lock released before any Python runs, so a callback calling `call_soon` itself can't deadlock -- its entry runs next frame; `dispatch::log_uncaught_exception` widened to `pub(crate)`)
- Step 4: lifecycle semantics -- callables queued before `run()` run on the first frame; callables queued after `run()` returns stay queued for a later `run()` rather than being silently dropped; documented either way — ✅ (before-`run()` is proven live; after-`run()` is untested end-to-end, since that needs two `App.run()` calls in one process, which this suite avoids and `test_terminal.py` already records as unsupported on one `App`)
- Step 5: tests -- Rust unit tests for the queue/drain logic; pytest cases that run a real bounded `App.run()` in a fresh subprocess each (the `test_tracing.py` pattern, per the known "no second `App.run()` in one pytest process" constraint): a `threading.Thread` calls `handle.call_soon` mid-run and the callable runs on the main thread (checked via `threading.get_ident()`), changes a node, and a raising callable doesn't stop the loop or later callables; plus in-process tests for `TypeError` on a non-callable and for calling `call_soon` from a background thread without an exception — ✅ (4 Rust tests; 9 pytest cases in `tests/test_thread_handle.py`, the live ones skipping honestly when no frame ever ran; also pins that calling `App` itself from a background thread raises pyo3's `PanicException`, a `BaseException`; pytest 923 passed, 2 skipped)
- Step 6: `_core.pyi` stubs (`App.thread_handle`, `LoopHandle`), `tre/__init__.py` export, `mypy --strict` on the stub clean — ✅

### Phase 2 — Example, Docs, Verification ✅
- Step 1: `examples/threadsafe_reload.py` -- a background thread (stdlib only, no new dependency) that watches a view's source via `os.stat` and hands `view.reconcile(spec=...)` to the loop through `call_soon`, the shape Tesserae's file-change watcher will take — ✅ (works on a temp copy of `hot_reload.yaml`; asserts the reload landed whenever a frame ran, and only skips when none did)
- Step 2: MkDocs -- `api/python/app.md` gains `thread_handle`/`LoopHandle`; `declarative-views.md`'s "Hot reload" section gains "Hot reload inside `App.run()`", replacing the headless-only caveat; `mkdocs build --strict` clean — ✅ (also `LoopHandle` in `api/python/index.md`, whose class count was already wrong since M85 and is now dropped rather than kept as a number that drifts)
- Step 3: full standing chain -- `cargo check`/`clippy -D warnings`/`fmt --check`/`cargo test --workspace --release`/`maturin develop --release`/`pytest tests/`/all examples/`demo/showcase.py` — ✅ (`cargo test --workspace --release` 47 suites, 540 passed, 0 failed; pytest 923 passed, 2 skipped; all 89 examples plus `demo/showcase.py` run clean)

**Real finding while verifying:** a `max_frames`-bounded run counts idle frames too, and an idle frame costs microseconds -- 6000 frames finished in 63 ms. A test or example that waits on a background thread with any delay at all can lose that race and pass or fail by luck. The first draft of the live pytest passed only because its worker thread happened to be fast. Both the tests and `examples/threadsafe_reload.py` were made deterministic -- the first-frame callable waits for the background thread to finish queueing -- without weakening what they prove: the queueing still happens on a genuinely different thread.

**Idle wake-up is covered, not just busy frames:** `PlatformEvent::Wake` is what wakes a `ControlFlow::Wait` loop (M31 Phase 6 already proves that path for terminal output); a bounded `max_frames` run forces `ControlFlow::Poll` (M83's finding), so the pytest cases prove callback delivery and threading, while the idle path rests on the same `Wake` mechanism `Terminal` already exercises live.

## Future Work — `vello_hybrid` Fork for Real GPU-Level Partial Redraw

**Tracked as [`tre` issue #4](https://github.com/mindderivative/tre/issues/4), milestone `0.3.2` (2026-09-24).** Not a milestone in this file, still documented only, per explicit user instruction ("Add the vello_hybrid fork for future performance feature"), scoped down via `AskUserQuestion` to "document it only": no git remote/fork created, no `Cargo.toml` change, no code written. Recorded here in full so a future milestone can start directly from real, cited facts instead of re-investigating from scratch; the GitHub issue carries the identical content for anyone tracking work through issues rather than this file.

**Real target to fork:** `vello_hybrid = "0.2.0"` — confirmed via direct read of the vendored crate's own `Cargo.toml` (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/vello_hybrid-0.2.0/Cargo.toml`), `repository = "https://github.com/linebender/vello"` — a monorepo (the `vello`/`vello_cpu`/`vello_hybrid` variants §7.2/§15 already named as "early-stage, no API stability guarantee, uneven parity" live together there), not a single-crate repo. **Real, load-bearing risk, stated directly and not to be glossed over when this is picked up:** its own `CHANGELOG.md` documents that "the scene scheduling and rendering architecture has been rewritten" since 0.1.0 — a fork tracking this crate's own upstream is tracking active architectural churn, not a stable target; every real merge from upstream would need to be re-checked against the patch below.

**The real, minimal patch this milestone's own investigation identified (exact file:line references, `mod.rs` = `src/render/wgpu/mod.rs` in the vendored source):**
1. `Renderer::render`'s own public signature (`mod.rs:227-237`) takes no scissor/dirty-rect parameter and no `clear: bool` — both need adding. `render_scene` (the private method `render` calls internally, signature at `mod.rs:411-424`) already has a real `clear: bool` parameter (`mod.rs:421`) — `render()` itself just hardcodes `clear = true` at the one real call site (`mod.rs:278`). The forkless path (`render_to_atlas`, `mod.rs:374`) already calls it with `clear = false`, proving the `false` path is exercised and correct internally — it's simply unreachable from the public API today.
2. `Self::clear_view` (`mod.rs:465-513`) is the dedicated full-target clear pass (`LoadOp::Clear(TRANSPARENT)`, no scissor) that runs whenever `clear` is true. A real scissored variant would need its own `set_scissor_rect` call before the fill, the identical real technique `Renderer::clear_atlas_region` (`mod.rs:632-682`, `set_scissor_rect` at `mod.rs:664`/`676`) already proves works in this exact codebase, just currently `pub(crate)`-scoped to atlas layers rather than the user-facing view.
3. Every real drawing pass in this file already uses `LoadOp::Load` (confirmed at `mod.rs:2839`, `2963`, `3092`, `3175`, `3215` per this milestone's own investigation) — meaning the *drawing* passes already preserve existing texture contents; only the dedicated `clear_view` pass actively wipes the target. A real scissored-clear variant, scoped to a caller-supplied dirty rect, is the one missing piece.
4. `Config` already carries `strip_offset_x`/`strip_offset_y` (`src/render/common.rs:336-338`) but both real wgpu call sites hardcode `0` (`mod.rs:1953`, `2401`) with no public setter — a second, smaller real API gap worth exposing alongside the scissor/clear one if this fork is ever started, though not load-bearing for partial redraw itself.

**What TRE's own side would additionally need, independent of the vello_hybrid patch above:** `engine-py::app.rs` currently renders into `surface.get_current_texture()` (confirmed at the real per-frame render call) — a real wgpu swapchain image that rotates across 2-3 buffers and does **not** retain the previous frame's own pixels. Even a patched `vello_hybrid` exposing a real scissor/no-clear path would need TRE to own a persistent offscreen `wgpu::Texture` (rendered into across frames, scissored-updated only in the dirty region) plus a full-target blit from that texture to the acquired swapchain image every frame — a real, separate piece of engine-py-side infrastructure this fork alone doesn't solve.

**Real dirty-region tracking this fork would also need, not yet designed at all:** today's `Tree.dirty: bool` (M29 Phase 1) is a coarse whole-frame yes/no flag — real scissored redraw needs a genuine dirty *rect* (or a small set of them) accumulated per frame from whatever actually changed (an `Animated<T>` still ticking, a `Tree::dispatch` mutation), unioned into the minimal real bounding rect(s) to pass through the patched `render()` call above. No design work on this has been done; it is a real, separate, non-trivial piece of `engine-core`/`engine-render` work on top of the vello_hybrid patch itself.

**Honest sizing, for whoever scopes this next:** three real, separate pieces of work (the vello_hybrid patch, TRE's own offscreen-texture+blit machinery, and real dirty-rect tracking to feed it), plus ongoing fork-maintenance risk against an actively-rewritten upstream — genuinely larger than any single phase this project has scoped so far. A real `AskUserQuestion` scope-confirmation pause (the established precedent for Code Folding/Terminal Mouse Selection/this exact M34 decision) is very likely warranted again before committing to building it, not just scoping it directly the way M33's mechanical refactors could be.
