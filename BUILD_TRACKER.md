## Milestone 50 — Theme-Driven Shape & Elevation for the Imperative MD3 Catalog (§5, §7, §7.1)

**Status: ✅ Complete — all 5 phases.** User-directed: "Scope the corner-radius/elevation to use the new theme pattern. I would like the theme backend complete before re-theming everything else" -- explicitly reprioritizing this ahead of M51/live re-theme (M49's own originally-scoped "up next"). Scoped via a formal plan (`EnterPlanMode`/`ExitPlanMode`).

**Real investigation before designing, via a dedicated Explore agent, exhaustive rather than sampled:** every one of the 56 `add_*` factories in `window_factory.rs` (7,581 lines) was individually classified. **28 of 56 have a real, themeable corner radius; 14 of those 28 also have a real, themeable elevation; the other 28 have neither** (custom-painted `NodeKind`s with no `Rect` shape at all -- Checkbox/Slider/Switch/Icon/Image/Progress/Terminal/etc. -- or deliberately flat/square MD3 rows -- menu item, list row, divider, status bar). Only `add_fab` (size: small/default/large) and `add_toolbar` (docked/floating) genuinely pick between multiple corner-radius values by variant; every other themeable component uses one fixed value regardless of its own color variant. Two factories (`add_split_button`, `add_button_group`) have a *second*, genuinely distinct corner-radius concept -- an interaction-driven "tightened" shape on hover/press, not the same thing as their own rest-state radius.

### Phase 1 — Mechanism ✅
- Step 1: `ThemeSpec.components` / `ComponentOverride` — ✅ (`crates/engine-spec/src/theme.rs`: new `ComponentOverride { corner_radius: Option<f64>, elevation: Option<f64> }` plus `ThemeSpec.components: HashMap<String, ComponentOverride>` -- a deliberately separate namespace from `styles:` (which only ever reaches the 7 declarative `NodeKindSpec` kinds), keyed by `"<component>"` (applies regardless of variant) or `"<component>.<variant>"` (overrides just one). 3 new parse tests.)
- Step 2: `ThemeState.components` / `shape()` / `elevation()` — ✅ (`crates/engine-py/src/window.rs`: real 2-tier, **per-field** lookup -- variant-specific key checked first, bare key second, `None` if neither has *that specific field* set. **Real bug caught and fixed before any factory used it, by a dedicated unit test, not by inspection:** an early draft checked "does a variant-specific entry exist at all" before falling through to the bare key -- meaning a variant entry setting only `elevation` would incorrectly block the bare key's own `corner_radius` from ever being found. Fixed to look up each field independently. Wired into `Window.set_theme`'s existing `custom_theme` parsing (temporarily `#[allow(dead_code)]` until Phase 2 gave it a real caller, removed once Phase 2 landed). 5 new unit tests, GIL-free (`ThemeState`/`ComponentOverride` are plain Rust): no-override-returns-none, bare-key-read, variant-beats-bare, the shadowing bug above, elevation mirrors shape's own precedence.)

### Phase 2 — Buttons & FAB Family ✅
- Step 1: `add_button`, `add_icon_button`, `add_fab`, `add_extended_fab`, `add_segmented_button`, `add_toolbar` — ✅ (`crates/engine-py/src/window_factory.rs`: `resolve_button_colors` gained a `component: &str` parameter so its own elevation lookup can use a different key per real caller (`"button"` for `add_button`, `"icon_button"` for `add_icon_button`) even though both share the same color-resolution logic; corner radius resolved inline at each call site, since it depends on a caller-supplied dimension the shared resolver has no access to. `add_fab`'s corner radius is keyed by *size* (small/default/large -- a real, fixed per-variant choice, not a continuous formula); its elevation is keyed with no variant at all, since real MD3 anatomy makes FAB elevation flat regardless of size or color.)
- Step 2: `add_split_button`, `add_button_group` — ✅ (**A real, load-bearing bug caught and fixed before it shipped, not by inspection alone:** both factories' own hover/press shape-morph code used to recompute `height / 2.0` as a fresh, independent literal for their `interactive_shape`/`press_interactive_shape` pairs -- completely bypassing whatever `add_button` itself had just resolved for `paint.corner_radius` moments earlier. A themed button's own painted *shape* would have silently disagreed with its own `corner_radius` field the moment a theme overrode `"button"`. Fixed by resolving the theme override *once* (recomputing the identical value `add_button` itself already used internally -- same key, same variant, same height, guaranteed to agree, not read back from the tree, which would reach the same number more roundaboutly) and reusing it for both the rest-state radius and the shape-morph geometry. The "tightened" hover/press radius gets its own, genuinely distinct `"split_button.tightened"`/`"button_group.tightened"` key -- no equivalent concept exists in plain `add_button` to inherit it from.)
- Verification: 12 new pytest tests -- variant-specific override + no-leak-to-other-variants, bare-key-applies-to-every-variant, `icon_button` has its own key distinct from `button` (including the MD3-internal `"text"` variant-name translation for `"standard"`), FAB's size-keyed corner vs. variant-less elevation, `extended_fab`'s own distinct key, `split_button`'s leading button inheriting the `button` key, both `.tightened` keys not raising (no Python-facing readback for `interactive_shape`/`corner_radii_override`), and a full unthemed-defaults-preserved sweep across all 8 factories.

### Phase 3 — Containers & Surfaces ✅
- Step 1: `add_chip`, `add_card`, `add_tooltip`, `add_dialog`, `add_snackbar`, `add_popover`, `add_side_sheet`, `add_navigation_drawer`, `add_search_bar`, `add_search_view` — ✅ (`resolve_card_colors` gained the same `component`-driven elevation-lookup widening `resolve_button_colors` established in Phase 2. `add_side_sheet`/`add_navigation_drawer` apply their override through `corner_radii_override` (per-corner rounding), not the plain `corner_radius` field -- no Python-facing readback for that value, confirmed and tested as a "does not raise" case. Every factory that only *coincidentally* shares a Rust `const` with an unrelated factory today (`add_search_view` reusing `DIALOG_CORNER_RADIUS`, `add_navigation_drawer` reusing `SIDE_SHEET_CORNER_RADIUS`) still gets its own distinct theme key, per this milestone's own established "shares a number today, not a reason to couple overrides" convention (`crates/engine-spec/src/theme.rs`'s own doc comment).)

### Phase 5 — Shipped Defaults, Docs, Example ✅
- Step 1: shipped `default_theme.yaml`'s `components:` section — ✅ (`crates/engine-py/assets/default_theme.yaml`: every safe, fixed default value copied byte-for-byte from `window_factory.rs`'s own real `const`s, verified by direct read immediately before writing each one, not recalled from memory or the earlier investigation's own prose summary. **A real correctness constraint identified and honored, not glossed over:** components whose real default is a *formula over a caller-supplied dimension* -- `add_button`/`add_icon_button`/`add_segmented_button`/`add_toolbar`'s own corner radius, `add_button_group`'s own tightened shape -- were deliberately given **no** entry in the shipped file at all. 1. `Renderer::render`'s own public signature (`mod.rs:227-237`) takes no scissor/dirty-rect parameter and no `clear: bool` — both need adding. `render_scene` (the private method `render` calls internally, signature at `mod.rs:411-424`) already has a real `clear: bool` parameter (`mod.rs:421`) — `render()` itself just hardcodes `clear = true` at the one real call site (`mod.rs:278`). The forkless path (`render_to_atlas`, `mod.rs:374`) already calls it with `clear = false`, proving the `false` path is exercised and correct internally — it's simply unreachable from the public API today.
2. `Self::clear_view` (`mod.rs:465-513`) is the dedicated full-target clear pass (`LoadOp::Clear(TRANSPARENT)`, no scissor) that runs whenever `clear` is true. A real scissored variant would need its own `set_scissor_rect` call before the fill, the identical real technique `Renderer::clear_atlas_region` (`mod.rs:632-682`, `set_scissor_rect` at `mod.rs:664`/`676`) already proves works in this exact codebase, just currently `pub(crate)`-scoped to atlas layers rather than the user-facing view.
3. Every real drawing pass in this file already uses `LoadOp::Load` (confirmed at `mod.rs:2839`, `2963`, `3092`, `3175`, `3215` per this milestone's own investigation) — meaning the *drawing* passes already preserve existing texture contents; only the dedicated `clear_view` pass actively wipes the target. A real scissored-clear variant, scoped to a caller-supplied dirty rect, is the one missing piece.
4. `Config` already carries `strip_offset_x`/`strip_offset_y` (`src/render/common.rs:336-338`) but both real wgpu call sites hardcode `0` (`mod.rs:1953`, `2401`) with no public setter — a second, smaller real API gap worth exposing alongside the scissor/clear one if this fork is ever started, though not load-bearing for partial redraw itself.

**What TRE's own side would additionally need, independent of the vello_hybrid patch above:** `engine-py::app.rs` currently renders into `surface.get_current_texture()` (confirmed at the real per-frame render call) — a real wgpu swapchain image that rotates across 2-3 buffers and does **not** retain the previous frame's own pixels. Even a patched `vello_hybrid` exposing a real scissor/no-clear path would need TRE to own a persistent offscreen `wgpu::Texture` (rendered into across frames, scissored-updated only in the dirty region) plus a full-target blit from that texture to the acquired swapchain image every frame — a real, separate piece of engine-py-side infrastructure this fork alone doesn't solve.

**Real dirty-region tracking this fork would also need, not yet designed at all:** today's `Tree.dirty: bool` (M29 Phase 1) is a coarse whole-frame yes/no flag — real scissored redraw needs a genuine dirty *rect* (or a small set of them) accumulated per frame from whatever actually changed (an `Animated<T>` still ticking, a `Tree::dispatch` mutation), unioned into the minimal real bounding rect(s) to pass through the patched `render()` call above. No design work on this has been done; it is a real, separate, non-trivial piece of `engine-core`/`engine-render` work on top of the vello_hybrid patch itself.

**Honest sizing, for whoever scopes this next:** three real, separate pieces of work (the vello_hybrid patch, TRE's own offscreen-texture+blit machinery, and real dirty-rect tracking to feed it), plus ongoing fork-maintenance risk against an actively-rewritten upstream — genuinely larger than any single phase this project has scoped so far.
