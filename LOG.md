# Log: M4 Phase 1, Step 1 — Real Input Dispatch Core (§4, §7.3, §9, §10, §11.10)

Corresponds to `PLAN.md`/`BUILD_TRACKER.md` M4 Phase 1, step 1 of a sketched 3. M3 (all 15 of §14's Suggested Build Order steps) is complete; no M4 is sequenced anywhere in `ARCHITECTURE.md`. This picks up the single most consistently recurring finding from M3 (checked directly at every interaction-dependent step — 7, 9, 11, 12, 13, 14, 15): real pointer/keyboard `InputEvent`/`AppHandler` dispatch and hit-testing don't exist anywhere in this codebase. Every one of those steps exposed a direct, programmatic `Tree` method instead (`spawn_ripple`, `open_overlay`, `set_splitter_position`, `apply_active_tab`, `set_virtual_list_window`) and explicitly deferred real wiring to whichever step built it first. This is that step — core mechanism only, entirely inside `engine-core`, no `winit`/`pyo3` yet.

## What happened

**New `engine-core/src/input.rs`**: `InputEvent` (`PointerMoved`/`PointerPressed`/`PointerReleased` carrying `position: kurbo::Point` + `button: PointerButton`; `KeyPressed`/`KeyReleased` carrying a minimal `Key`), `PointerButton` (`Primary`/`Secondary`/`Middle`, matching `winit::event::MouseButton`'s three real variants 1:1 for a lossless future translation), `Key` (`Tab`/`Enter`/`Space`/`Escape` only — deliberately not a general key-code/character-input mapping, matching §10's own stated minimal keyboard model exactly; nothing before a real text-entry `NodeKind` needs more), `DispatchOutcome` (`None`/`Activated(NodeId)`), and `AppHandler` (§4's own named trait — kept to the one meaning-dependent hook `Tree::dispatch` can't resolve itself, `on_activated(node)`; everything mechanical stays inside `Tree`, per §2 Design Principle 6).

**`Tree` gains four real methods, in `tree.rs`**:
- `hit_test(root, point) -> Option<NodeId>` (§11.10): a recursive reverse-paint-order walk (last child first — the topmost, since §6's own children-list-order-is-paint-order convention means the last child paints on top) testing rect containment via the already-existing `absolute_position`/`layout().size`. Every node, including containers, is a valid hit target by its own bounds — matching the architecture's own text exactly, not narrowed to "leaf nodes only."
- `update_hover(root, point, hover_opacity, duration, now) -> Option<NodeId>`: the literal, concrete fulfillment of §7.3's own text — "hover needs no new dispatch mechanism — it falls out of hit-testing, run every pointer-move... entirely inside `engine-core`." Only animates a node that already opted into `InteractionState` (checked via `node.interaction.as_mut()`, never `interaction_mut`, which would wrongly lazily-create one on every hover) — Design Principle 6's "only a node that opts in pays the cost," applied for real this time, not just described. `hover_opacity`/`duration` are caller-supplied, not hardcoded: `engine-core` stays MD3-agnostic (§1 Locked Decisions) — the real MD3 hover value is `engine-md3`'s to supply later, the same generic/preset split `MotionCurve`/`engine_md3::motion::STANDARD` already uses.
- `move_focus(root, direction, focus_ring_opacity, duration, now)`: §10's minimal keyboard focus model, for real — Tab/Shift-Tab moves `focused` in tree order, wrapping at both ends. "Interactive" means `access.actions` is non-empty — the real, already-existing signal M3 step 7's own button test sets (`AccessNodeData::new(Role::Button).with_action(Action::Click)`), not a new field manufactured for this step. Animates `focus_ring` the same opt-in-only way `update_hover` animates `hover_opacity`.
- `dispatch(root, event, config: &InteractionConfig, now) -> DispatchOutcome`: the one real top-level entry point a future `engine-platform` calls. Every mechanical consequence (hover, focus movement, ripple-spawn-on-press) happens here; `DispatchOutcome::Activated` is the sole meaning-dependent outcome, left for the caller's own `AppHandler` to interpret. A click requires the *same* node and the *same* (primary) button on both press and release — a press then a drag-off to a different node (or no node) produces no activation, matching every real UI toolkit's own click semantics.

`InteractionConfig` bundles the MD3-value inputs (`hover_opacity`/`hover_duration`/`focus_ring_opacity`/`focus_ring_duration`/`ripple_radius`/`ripple_opacity`/`ripple_duration`) `dispatch` needs — deliberately no `Default` impl, so a caller/test must state real values rather than inherit an unstated MD3 opinion baked into `engine-core`.

**Real, verified-not-assumed API-drift finding**: §10's own text says Enter/Space "dispatches `accesskit::Action::Default`." Checked directly against the pinned `accesskit = "0.25.0"`'s real `Action` enum (`accesskit-0.25.0/src/lib.rs`) before writing any code: there is no `Action::Default` variant. The real, equivalent variant is `Action::Click` ("do the equivalent of a single click or tap") — already the exact action M3 step 7's own button test uses, so this isn't inventing a new convention, just making an existing one do real work for the first time.

**Ripple stays single-shot** (`InteractionState::spawn_ripple`'s existing combined press+release approximation) for this step, not upgraded to `interaction.rs`'s own described two-phase press/hold/release model — that's real, separate scope (tracking which ripple is still "held down" across a press/release pair, MD3's actual timing curves), genuinely bigger than "make real events reach the tree at all." Stated here, not silently dropped.

**Real bugs found and fixed via testing, not assumed correct on the first try**: writing the hit-testing tests surfaced that this `slotmap` version reserves index 0 (real `NodeId`s in a fresh `Tree` start at `1v1`, not `0v1`) — a genuinely new, previously-unconfirmed fact, discovered because a test's own expected-ID arithmetic was off by one against it. Also found two real test-construction bugs of my own: an "outside every node's bounds" test picked a point still inside the root container's own full-canvas bounds (root is a real hit target too, by design — not a bug in `hit_test`, a wrong assumption in the test); and an overlay-hit-testing test used a 300x300 full-canvas node as `open_overlay`'s own anchor, which placed the overlay menu at `anchor_y + anchor_height = 300` — entirely off-screen — rather than near the top where the test assumed. Fixed by testing a genuinely-outside point, and by giving the overlay test a proper small anchor button (80x20, matching the existing `open_overlay_positions_below_its_anchor_and_appends_to_root` test's own precedent) instead of reusing the full-canvas background as the anchor.

## Verification

6 new tests, each isolating one claim: `hit_test_reaches_the_topmost_of_two_overlapping_siblings`, `hit_test_misses_entirely_outside_every_nodes_bounds`, `hit_test_reaches_an_appended_overlay_over_background_content` (reusing step 13's own overlay-proof shape — the overlay wins over the background it's stacked above, same append-order-is-paint-order convention), `update_hover_only_animates_nodes_that_already_opted_into_interaction_state`, `update_hover_fades_the_old_node_out_and_the_new_one_in_on_a_real_change`, `move_focus_cycles_only_through_interactive_nodes_in_tree_order_wrapping_at_both_ends`, `dispatch_activates_only_a_same_node_primary_press_and_release_pair`. All passed after fixing the three test-construction issues above. `engine-core` now at 32 unit tests.
